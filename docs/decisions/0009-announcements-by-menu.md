# 0009: 告知は、右クリックで選んだものだけ相手のサーバーに出す

- 日付: 2026-11-10
- 状態: 採用中（方針を変えたら、このファイルは書き換えず、新しい ADR を作ってここを「廃止（NNNN で置き換え）」にする）
- 関連: [0001](0001-sync-scope-and-bot-permissions.md)（同期の範囲）、[0005](0005-mentions-and-roster-command.md)（通知・常時接続）、[0008](0008-discord-py.md)（コマンドの受け方）、要件 F2・F16

## 判断1: Discord の「フォロー」をやめて、NepSync が写す（発案者）

**困っていたこと**：KGU の告知に同期チャンネルの発言へのリンクを書いてフォローで CID に流すと、CID でも KGU の発言へのリンクのままになる。CID の人は開けない。フォローで届いた投稿は、届いた側の誰にも（bot にも）書き換えられない。

**決めたこと**：告知チャンネルのフォローをやめる。設定に書いた告知チャンネルの組（KGU の告知 ↔ CID の告知）の間で、NepSync が Webhook で写す。本文の書き換え（リンク・呼び出し）は、同期チャンネルと同じものを使う。写したあとの編集・削除・リアクション・投票も、同期チャンネルと同じく相手に届く。

**検討した選択肢**：

- 案A（採用）：フォローをやめて NepSync が写す。リンクが相手側の発言を指す
- 案B（却下）：右クリックで「相手のサーバーのリンク」を出すコマンドを足して、告知に両方のリンクを書く。作業は小さいが、開けないリンクが告知に混ざり、毎回手間がかかる

**引き換え**：

- 相手のサーバーでは「KGU #お知らせ」名義ではなく、書いた人の名前とアイコンで出る
- 出るまでに数十秒かかる（下の判断2）
- 告知チャンネルはカテゴリの外にあることが多いので、構造（名前・並び順など）は同期しない。組は設定に ID で書く

## 判断2: 告知は既定では流さず、右クリックの「アプリ」で選んだものだけ出す（発案者）

**決めたこと**：告知チャンネルには相手に出したくない告知もあるので、自動では流さない。発言の右クリック →「アプリ」に2つのメニューを足す。

- 「相手のサーバーにも出す」：その告知を相手の告知チャンネルに写す。終わったら、写しへのリンクを押した人にだけ見せる
- 「相手のサーバーから下げる」：相手の写しだけを消す。元の告知は残る。元の告知を消したときは、これまでどおり写しも消える。写しの側で押しても下げられる

メニューを押すと、bot のスレッドが SQLite の `announce_requests` に「この発言 ID を出す・下げる」を書き、同期の本体が次の回（最大で25秒ほど後）に処理する。同期の本体が1本の流れで順に動く決まり（overview）を崩さないため。本文は Neplector の `/v1/messages` から取る。

**使える人**（発案者）：そのチャンネルで「メッセージの管理」を持つ人と、その告知を書いた本人。本人も使えるようにするので、Discord の側でメニューを隠すことはできず、全員に見える。使えない人が押すと、そう答える。

**守り**：

- メニューを押したとき、Discord は対象の発言の本文もこちらに送ってくる（Message Content の権限が無くても、対象の発言は届く決まり）。**この本文は使わず、保存もログへの書き出しもしない**。使うのは発言の ID とチャンネル ID、書いた人の ID だけ。「発言の知らせを Discord から受けない」の約束は、人がメニューを押したときに1件届くだけなので崩れない（スラッシュコマンドと同じ扱い。0005 判断3）
- `announce_requests` に入れるのは ID と結果の短い記号だけ。1日たったら消す
- 写しの側で「出す」を押しても出さない（輪にしない）。スレッドの中の発言は対象にしない
- Neplector に本文が無い発言（告知を出す前の古い発言、外れた人の発言、bot の投稿）は出せない。そう答える

**検討した選択肢**：

- 案A（採用）：右クリックのメニュー。告知を書いたあとに、その場で選べる
- 案B（却下）：告知の文に印（例：先頭に `[共有]`）を書いたら流す。手軽だが、印が読む人にも見える。付け忘れたあとに直す手段も別に要る
- 案C（却下）：全部流して、出したくないものだけ下げる。一度は相手に見えてしまう

## 判断3: 両方向にする（発案者）

**決めたこと**：組は両方向に使える。どちらの告知チャンネルも Neplector がもう読んでいる（2026-11-10 に確かめた。KGU は「アナウンス系」、CID は「インフォメーション」のカテゴリ）ので、Neplector の設定は変えずに始められる。Neplector が読んでいない告知チャンネルで「出す」を押すと、記録が無いので出せないと答える。

## 判断4: 告知では `member` ロールだけ、相手のサーバーでも通知を鳴らす（発案者）

**決めたこと**：告知の中のロールの呼び出しのうち、設定 `announce_ping_roles`（今は `member`）に書いた名前のロールは、相手のサーバーの同じ名前のロールの呼び出しに書き換えて、通知を鳴らす。両方のサーバーに、正式に加入した参加者全員が持つ `member` ロールがあるため。ほかのロール・`@everyone`・`@here` は、これまでどおり名前の文字にして鳴らさない（F16）。同期チャンネルの発言は変えない。

**引き換え**：同じ名前のロールが相手に無ければ、名前の文字にして鳴らさない。ロールを「誰でもメンションできる」にしていない場合、Webhook から鳴らせるかは実機で確かめる（下）。

## 判断5: 相手のサーバーで開けないリンクがあれば、出したあとに警告する（発案者）

**決めたこと**：「相手のサーバーにも出す」で出した告知に、元のサーバーを指すリンクのうち相手のサーバーで開けないものがあれば、押した人への答えに警告を付ける。

- 発言が同期されていないリンク：相手側ではチャンネルへのリンクになる（F18 のまま）、と書く
- 同期していないチャンネルへのリンク：元のサーバーのリンクのままで、相手の人は開けない、と書く
- ほかのサーバーへのリンクは見ない。同期チャンネルの自動の同期では警告しない（知らせる相手がいない）
- 出すのは止めない。直すときは「下げる」か、元の告知の編集（写しにも届く）
- `announce_requests.warning` に残すのはリンク（ID だけの URL）と種類だけ。本文は残さない

**検討した選択肢**：

- 案A（採用）：出してから警告する。押す手間は今のまま。気づいたら下げるか直せる
- 案B（却下）：出す前に警告して、「それでも出す」のボタンで確かめる。一度も相手に見えずに済むが、毎回の手間とボタンの仕組みが増える

## 実機で確かめること

- Webhook の投稿で `member` ロールの通知が鳴るか。鳴らなければ、相手の告知チャンネルで bot に「@everyone、@here、全てのロールにメンション」を許可するか、ロールを「誰でもメンションできる」にする
- メニューを押したときに届く発言の本文が、ログ（`run.log`）に出ていないこと

## 用語メモ

- Webhook：bot の代わりに、名前とアイコンを変えて投稿できる仕組み。同期の写しはこれで出している
- フォロー（アナウンスチャンネルのフォロー）：ほかのサーバーのアナウンスチャンネルの投稿を、Discord が自分のサーバーにそのまま写す仕組み
